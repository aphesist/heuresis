## 1. Optimiser-to-system contracts (GEPA, DSPy, OpenEvolve, ShinkaEvolve, AlphaEvolve, DGM/HGM, SICA, ADAS, Gödel Agent, AI Scientist-v2, 2026 follow-ups)

### Takeaway
Every optimiser in this family uses the same narrow contract. The system exposes (a) a mutable surface of text or code and (b) a scoring function over a batch that returns per-example scores plus optional rich feedback or artifacts. The optimiser never owns the evaluator. The practical risk across systems is that the evaluator is only protected by convention (OpenEvolve does not enforce block boundaries), so the retrieval engine adapter must enforce immutability itself.

### Cited Findings

**GEPA `GEPAAdapter` (gepa-ai/gepa, `src/gepa/core/adapter.py`)**
- It is a `Protocol[DataInst, Trajectory, RolloutOutput]` with these signatures. `evaluate(self, batch: list[DataInst], candidate: dict[str, str], capture_traces: bool = False) -> EvaluationBatch[Trajectory, RolloutOutput]`; `make_reflective_dataset(self, candidate: dict[str, str], eval_batch: EvaluationBatch[Trajectory, RolloutOutput], components_to_update: list[str]) -> Mapping[str, Sequence[Mapping[str, Any]]]`; and an optional attribute `propose_new_texts: ProposalFn | None = None`. — [adapter.py](https://raw.githubusercontent.com/gepa-ai/gepa/main/src/gepa/core/adapter.py) (paraphrased by the fetch tool; the signatures were returned, the docstring text was paraphrased)
- `EvaluationBatch` fields: `outputs: list[RolloutOutput]`, `scores: list[float]`, `trajectories: list[Trajectory] | None = None`, `objective_scores: list[dict[str, float]] | None = None`, `num_metric_calls: int | None = None`. — same source
- Contract rules (paraphrased from the docstrings): `evaluate` must build the full system from each component's text, run it on the batch, and return per-example scores. Lengths of outputs and scores must equal the batch length. It must not mutate inputs. Failed examples should get a fallback score such as 0.0. Trajectories are required only when `capture_traces=True`. `make_reflective_dataset` returns JSON-serialisable per-component records (inputs, outputs, feedback text). Subsampling inside it should use a seeded RNG. A custom proposer receives the candidate, the reflective dataset and the components to update, and returns new text per component. It can update coupled components together. — same source
- A candidate is `dict[str, str]`, mapping component name to text. This is the "mutable surface" abstraction.

**`gepa.optimize(...)` (`src/gepa/api.py`)**
- Required: `seed_candidate: dict[str, str]`, `trainset: list[DataInst] | DataLoader`. Defaults for the rest: `valset=None` (the trainset is reused if omitted), `adapter=None`, `task_lm=None`, `evaluator=None`, `reflection_lm=None`, `reflection_lm_kwargs=None`, `candidate_selection_strategy="pareto"`, `frontier_type="instance"`, `skip_perfect_score=True`, `batch_sampler="epoch_shuffled"`, `reflection_minibatch_size=None` (the effective default is 3 with the epoch_shuffled sampler), `perfect_score=1.0`, `reflection_prompt_template=None`, `custom_candidate_proposer=None`, `module_selector="round_robin"`, `use_merge=False`, `max_merge_invocations=5`, `merge_val_overlap_floor=5`, `max_metric_calls=None`, `max_reflection_cost=None`, `stop_callbacks=None`, `logger=None`, `run_dir=None`, `callbacks=None`, `track_best_outputs=True`, `display_progress_bar=False`, `cache_evaluation=False`, `seed=0`, `raise_on_exception=True`, `val_evaluation_policy=None` (None means full evaluation of every validation example each time), `acceptance_criterion="strict_improvement"`, `sampling_strategy=None`, `selection_strategy=None`, `reflection_strategy=None`, plus wandb/mlflow flags. Keyword-only: `write_agent_state=False`, `reflective_dataset_enricher=None`. Returns `GEPAResult[RolloutOutput, DataId]`. — [api.py](https://raw.githubusercontent.com/gepa-ai/gepa/main/src/gepa/api.py)
- At least one stop condition is required (`stop_callbacks`, `max_metric_calls` or `max_reflection_cost`). If `run_dir` holds saved state, the run resumes from it. A `gepa.stop` file in `run_dir` triggers graceful shutdown. — same source
- Algorithmic contract from the paper: each iteration draws a minibatch of size b from D_feedback, scores the parent, proposes a child by changing one module's text, scores the child on the same minibatch, and only if the child's minibatch score strictly improves does it enter the pool and get evaluated on the full D_pareto. Every evaluation counts as a rollout. The paper says most of the budget goes to validation scoring. It does not give a dedicated overfitting mitigation and lists smaller or dynamic validation subsets as future work. — [GEPA paper](https://arxiv.org/html/2507.19457) (the page was truncated, so numeric b and n_pareto values were not visible)

**`dspy.GEPA` metric**
- Protocol `GEPAFeedbackMetric.__call__(gold, pred, trace, pred_name, pred_trace, program_trace=None) -> Union[float, ScoreWithFeedback]`. `pred_name` and `pred_trace` identify the predictor whose feedback is requested. At module level they are `None`. The metric may return `dspy.Prediction(score=..., feedback=...)`. If no feedback is returned, GEPA uses a default message stating the score. — [DSPy GEPA docs](https://dspy.ai/current/api/optimizers/GEPA/overview/)
- Metrics may also return `objective_scores`. `frontier_type` can be `"instance"` (default), `"objective"`, `"hybrid"` or `"cartesian"`, and the scalar score still decides acceptance. `compile(student, *, trainset, teacher=None, valset=None, **kwargs)`. `track_stats=True` gives `detailed_results` with `candidates`, `parents`, `val_aggregate_scores`, `total_metric_calls` and `best_candidate`. `gepa_kwargs={"frontier_type": "objective"}` passes through to `gepa.optimize`. — same source
- `warn_on_score_mismatch` (default True) warns when module-level and predictor-level scores diverge. — [search summary of dspy.ai docs](https://dspy.ai/diving-deeper/gepa-in-depth/)

**OpenEvolve (codelion/openevolve)**
- Evaluator is a file passed on the CLI: `python openevolve-run.py <initial_program.py> <evaluator.py> --config <config.yaml> --iterations N`. `evaluate(program_path)` returns an `EvaluationResult` with `metrics` and optional `artifacts`, or a plain dict, which is converted. Anything else becomes `{"error": 0.0}`. — [configuration.md](https://raw.githubusercontent.com/codelion/openevolve/main/docs/configuration.md), [evaluator.py](https://raw.githubusercontent.com/codelion/openevolve/main/openevolve/evaluator.py)
- Cascade: when `cascade_evaluation` is true, `evaluate_stage1(path)` runs first. If stage 1 fails `cascade_thresholds[0]`, its result is returned. Stage 2 runs if it exists. Stage 3 runs only if there is a second threshold and `evaluate_stage3` exists. A threshold check uses `combined_score` if present, otherwise the mean of numeric non-bool non-`error` metrics. If `evaluate_stage1` is missing, it falls back to direct evaluation. Timeouts: a stage-1 timeout returns `stage1_passed: 0.0, error: 0.0, timeout: True`. A later-stage timeout keeps earlier results. A direct-evaluation timeout returns `{"error": 0.0, "timeout": True}` with no retry. — evaluator.py
- Example evaluator (function_minimization): `evaluate` runs 10 trials, each under `run_with_timeout(..., timeout_seconds=5)` in a ThreadPoolExecutor. The fetch notes that the executor's `with` block waits for the thread, so a hung thread is not actually killed. `evaluate_stage1` runs a single trial and returns `runs_successfully` (1.0 / 0.5 / 0.0). `evaluate_stage2` just calls `evaluate`. — [example evaluator](https://raw.githubusercontent.com/codelion/openevolve/main/examples/function_minimization/evaluator.py)
- Artifacts side-channel: stored per program ID in `_pending_artifacts`, gated by the env var `ENABLE_ARTIFACTS` (default true). They reach prompts when `prompt.include_artifacts` is on, and failure artifacts include the traceback and `failure_stage`. Callers receive only the metrics dictionary. — evaluator.py, configuration.md
- Config keys seen (advanced example values, not defaults): `max_iterations: 1000` (overridden by `--iterations`), `diff_based_evolution: true` (SEARCH/REPLACE diffs; `full_rewrite_probability` example 0.2), `cascade_evaluation`, `cascade_thresholds` ([0.5] in the Python example), `enable_artifacts`, `use_llm_feedback`, `evaluator_args`, database `num_islands: 5`, `migration_interval: 20`, `population_size: 500`, `feature_dimensions: [complexity, diversity, performance]`, `feature_bins`. If `use_llm_feedback` and a `combined_score` exist, the final score is 70% evaluator plus 30% mean judge score. The defaults live in `configs/default_config.yaml`, which I did not retrieve. — configuration.md
- Block boundaries: `EVOLVE-BLOCK-START` / `EVOLVE-BLOCK-END` are documented in the README. The evaluator module has no reference to them. The whole `program_code` is written to a temp file and evaluated. I found no code in the fetched files that enforces the boundaries; whether the diff-application path enforces them was not visible (gap). — [README](https://raw.githubusercontent.com/codelion/openevolve/main/README.md), evaluator.py

**AlphaEvolve (arXiv 2506.13131, text extracted locally with pdftotext)**

### Inferences
- A thin adapter for the retrieval engine can mirror GEPA's shape: a mutable surface as `dict[str, str]` (prompt templates, rerank instructions, query-rewrite rules, routing config as serialised text), `evaluate(batch, candidate, capture_traces) -> (outputs, scores, trajectories, objective_scores)`, and a feedback builder. Multi-objective scores (`objective_scores`) can carry cost, latency, abstention rate and groundedness without changing the scalar the acceptance test uses.
- Because OpenEvolve and ShinkaEvolve do not enforce evolve-block boundaries in the files I read, the adapter should hash the immutable skeleton and the evaluator and reject any candidate that changes them. Do not rely on comment markers.
- ShinkaEvolve's `public`/`private` metric split and OpenEvolve's artifacts channel show the same design point. Feedback to the optimiser should be a curated, low-bandwidth channel, never raw sealed-set rows.
- The DGM small, then medium, then full cascade with a data-driven threshold is a reasonable template. It lacks any statistical test, so the protocol in section 3 should replace the thresholds.

## 2. Sample-efficient candidate evaluation under noise

### Takeaway
Fixed-budget best-arm identification (sequential halving) and racing both give large savings when per-prompt budgets are small (about 10 evaluations per prompt), and the advantage vanishes at about 30 per prompt in TRIPLE's experiments. Real optimisers (MIPROv2, GEPA) use minibatch screening followed by a full-set check, with small minibatches and no statistical test. For paired binary outcomes you can do much better by running an exact sign-test elimination on discordant pairs.

### Cited Findings
- TRIPLE (arXiv 2402.09723) casts prompt selection as fixed-budget best-arm identification with budget N total LLM trials. TRIPLE-SH (sequential halving) splits N into ceil(log2 |P|) equal phases and drops the worst half of active prompts each phase. TRIPLE-CR rejects the weakest prompt continuously using a large-deviation criterion. CLST (cluster prompts, then BAI) and GSE (reward model on embeddings) add structure. MEASURED (authors' experiments, GPT-3.5 and others, averaged over tasks): with 30 prompts and N=150, SH and CR beat uniform allocation by about 15% and 12%, and UCB by about 5% and 3%. With 150 prompts and N=100, CLST and GSE beat BO-EI by about 21% and 28%. At about 10 evaluations per prompt, CR, CLST and GSE beat uniform by 9.7%, 13.5% and 17.4%. At about 30 per prompt, all methods performed about the same. Inside APE, average ranks were 4.00 (uniform), 2.92 (CR), 1.58 (CLST), 1.50 (GSE). — [TRIPLE](https://arxiv.org/html/2402.09723) (read through 100k of 128k characters)
- MIPROv2 minibatching: each trial scores a candidate on a random minibatch. A full validation run on the best-averaging candidates happens every `minibatch_full_eval_steps` trials. Documented defaults conflict: the API reference says `minibatch_size=35`, `minibatch_full_eval_steps=5`, the deep-dive page says 25 and 10, and DeepEval says 25 and 10. — [DSPy MIPROv2](https://dspy.ai/api/optimizers/MIPROv2/), [deep dive](https://dspy.ai/deep-dive/optimizers/miprov2), [DeepEval](https://deepeval.com/docs/prompt-optimization-miprov2)
- GEPA minibatch gate: parent and child are scored on the same minibatch of size b (default 3 in the API). The child is only added and fully evaluated if it strictly improves. Reported: GEPA reached its best training-set performance with 79 to 737 training rollouts, but most of the total budget goes to validation scoring. — [GEPA paper](https://arxiv.org/html/2507.19457), [api.py](https://raw.githubusercontent.com/gepa-ai/gepa/main/src/gepa/api.py)
- Hyperband runs several successive-halving brackets with different starting budgets (eta = 2 example with r_min=1, r_max=8: from 4 configurations at budget 1 down to 1 at budget 8). Each rung keeps the best 1/eta and multiplies per-configuration budget by eta, and brackets spend roughly equal total budget. ASHA removes the synchronisation barrier so promotion is always allowed. — [mlr3hyperband docs, Orion ASHA code via search](https://cran.r-project.org/web/packages/mlr3hyperband/refman/mlr3hyperband.html), [ASHA implementation](https://orion.readthedocs.io/en/v0.2.2/_modules/orion/algo/asha.html) (secondary; the original Li et al. papers were not fetched)
- irace / F-Race: the first statistical test runs after T_first = 5 instances by default, then a test every T_each = 1 instance. Tests are the Friedman test with post-test, or a paired t-test. Losers are dropped once statistically worse than the best so far. The minimum instances per iteration is mu = 5. Number of racing iterations is floor(2 + log2(N_param)). — [López-Ibáñez et al. irace paper via search](https://unpaywall.org/10.1007%2F978-3-662-44320-0_4)
- AlphaEvolve's cascade is a fixed-threshold screen (see section 1).
- DGM filters with fixed subsets and a data-driven threshold (section 1).

### Inferences
- Savings are largest when (number of candidates) x (per-candidate cost) is large and noise is moderate. At about 30+ evaluations per candidate, TRIPLE's data suggest the smarter allocation buys almost nothing. So the gain is in the screening stage, not the final decision.
- Recommended design for paired binary outcomes on a shared example stream (my calculation, not from a paper): evaluate challenger and champion on the same minibatch. Let b = champion-wrong/challenger-right, c = the reverse, n_d = b + c. Eliminate the challenger early if the one-sided exact binomial P(X <= b | n_d, 1/2) is high enough, i.e., if c exceeds b by a margin. Concretely, a cheap rule: after at least 30 examples, drop if c - b >= 2*sqrt(n_d) (roughly z = 2 against the champion). Promote to the next stage only if b > c. Use stage sizes that grow geometrically (for example 50, 150, 450, then the full set), mirroring successive halving with eta = 3.
- Minibatch of 3 (GEPA default) or 25 to 35 (MIPROv2) is a proposal screen, not a statistical test. Treat the minibatch gate as a filter that only has to have high recall for good candidates. The real decision must come from the staged test in section 3.
- Reusing the same examples across rungs makes the rung statistics dependent. Use fresh examples per stage, or use anytime-valid methods (section 3).

## 3. Sequential and repeated promotion statistics

### Takeaway
For "promote forever", the right framework is an e-value per promotion decision combined with an online FDR procedure such as e-LOND, which has a proven guarantee under arbitrary dependence. Within a single promotion, use an anytime-valid test (betting confidence sequence or mSPRT-style e-process) on paired differences, with a non-inferiority margin for guardrail metrics.

### Cited Findings
- e-LOND (Xu and Ramdas, AISTATS 2024, arXiv 2311.06412; text extracted locally): the level at step t is alpha_t = alpha * gamma_t * (|R_{t-1}| + 1), where R_{t-1} is the discovery set so far and gamma_t is a nonnegative sequence summing to at most 1. Hypothesis t is rejected when e_t >= 1/alpha_t. Theorem 1: under arbitrary dependence on the e-values, FDR(R_t) <= alpha for every t, and e-LOND strictly dominates r-LOND applied to 1/E_t. The bound is sharp (Appendix C). The proof uses 1{E >= 1/alpha} <= alpha*E. The randomised Ue-LOND (alpha_t multiplied by U_{t-1} with U uniform) strictly dominates e-LOND in expectation. p-values can be calibrated with f_t(p) = (alpha*gamma_t * ceil((p*l_t)/(alpha*gamma_t) v 1))^{-1} to recover r-LOND. For comparison, LOND (alpha_t = alpha*gamma_t*(|R_{t-1}|+1)) needs independent or PRDS p-values, while r-LOND handles arbitrary dependence at a power cost. — [e-LOND paper](https://arxiv.org/pdf/2311.06412), [PMLR](https://proceedings.mlr.press/v238/xu24a.html)
- Follow-up (from a search summary, not read in full): online e-BH uniformly improves e-LOND. A critique says e-LOND loses power because levels come from pre-specified descending gamma sequences. — [search result listing](https://proceedings.mlr.press/v238/xu24a.html)
- Confidence sequences (Howard, Ramdas, McAuliffe, Sekhon, Annals of Statistics 2021): time-uniform intervals valid over an unbounded horizon, via stitching over geometrically spaced epochs. Parameters in the polynomial stitching example: eta = 2.04, h(k) = (k+1)^1.4 * zeta(1.4), and a start-time parameter m. Widths shrink at roughly 1/sqrt(t) up to log factors. — [Howard et al.](https://arxiv.org/pdf/1810.08240)
- Waudby-Smith and Ramdas, "Estimating means of bounded random variables by betting" (arXiv 2010.09686): confidence intervals and sequences for bounded means from betting, with predictable plug-in bets, empirical-Bernstein CS and a hedged capital process. It covers sampling without replacement. — [paper](https://arxiv.org/pdf/2010.09686.pdf)
- Exact McNemar: only discordant pairs matter. Conditional on n_d = b + c, b ~ Binomial(n_d, 1/2) under H0. Normal approximation is reasonable at n_d >= 25 (one source's cutoff). The exact test is conservative, and mid-p is a compromise. Power needs only the discordant probabilities pi_b, pi_c and the number of pairs. — [exact2x2 vignette](https://michaelfay-niaid.r-universe.dev/exact2x2/doc/exactMcNemar.pdf), [MedCalc](https://www.medcalc.org/en/book/mcnemar-test.php)
- Group-sequential designs: Lan-DeMets spending lets alpha be spent as a function of information fraction with unequal looks. O'Brien-Fleming type spends very little early (about 0.000004 cumulative at t = 0.25) and Pocock spends more evenly (about 0.0179 at t = 0.25). With four looks, the sample-size inflation is about 1.015 (O'Brien-Fleming) vs 1.17 (Pocock). One page's figures conflict with each other (final OBF z of 2.04 vs 1.96), so verify with gsDesign or rpact before use. — [MetricGate docs](https://metricgate.com/docs/group-sequential-design/) (a vendor page, low quality; treat numbers as leads)

### Inferences (my calculations, with stated assumptions)
- Fixed-n paired sample size. Using the Connor (1987) normal approximation [from memory, unverified], n = (z_a*sqrt(d) + z_b*sqrt(d - delta^2))^2 / delta^2, where d is the discordant fraction and delta the true improvement, one-sided alpha 0.05, power 0.8. I computed these numbers (also for alpha 0.005 in parentheses): d=0.10: delta=0.05 gives 245 (464), delta=0.03 gives 685 (1,295), delta=0.02 gives 1,544 (2,917), delta=0.01 gives 6,180 (11,676). d=0.05: delta=0.02 gives 771 (1,457), delta=0.01 gives 3,089 (5,837). d=0.20: delta=0.03 gives 1,372 (2,592). Lesson: a sealed set of a few hundred items only certifies improvements of about 5 points or larger. Detecting 1 to 2 points needs thousands of paired items, so most "promotions" of tiny gains cannot be certified honestly.
- Practical protocol: (1) stage A, unsealed dev items, cheap screen; (2) stage B, fresh items drawn from a rolling pool, paired exact sign test on discordant pairs plus a non-inferiority guardrail on every other metric (for example, one-sided lower confidence bound of Delta > -margin, margin about 1 to 2 points); (3) stage C, a sealed or freshly generated set, with a betting-style e-process on the per-item paired difference in {-1, 0, +1}. The e-process permits peeking and early stopping. Convert the final e-value to a decision with e-LOND across all promotion attempts, with gamma_t a slowly decaying sequence (for example proportional to 1/t^1.5 normalised), so total FDR across the infinite stream stays at alpha.
- Online FDR needs a convention for which hypothesis each promotion tests (H0: challenger is no better than champion). Under e-LOND, failed attempts spend no wealth, and each success increases future levels via (|R|+1). That fits "promote forever" because rare wins unlock more testing level.
- If candidates in the same generation share a champion, their e-values are dependent. e-LOND remains valid under arbitrary dependence, so that is a reason to prefer it over LORD/SAFFRON, which need independence or PRDS-type conditions [from memory, unverified].

### Gaps
- I did not retrieve primary text for alpha-investing, LORD/SAFFRON, mSPRT, or an e-process construction specific to paired binary outcomes. The sign-test e-process and the exact mSPRT form should be implemented from Waudby-Smith and Ramdas (2020) and Ramdas et al. "Game-theoretic statistics" and checked numerically.
- Non-inferiority sample-size formulas for paired binary data were not found in the search. The Connor-style formula above is from memory.
- Exact group-sequential boundaries were not verified against a reliable package. Use gsDesign or rpact.

## 4. Limits on sealed-set reuse

### Takeaway
Thresholdout permits many more adaptive evaluations than naive reuse only if the analyst rarely overfits, because the budget B counts only the queries where training and holdout disagree. The proved bound needs roughly n >= C * ln(m/beta)/tau^2 * min(B, sqrt(B ln(ln(m/beta)/tau))), so at tau = 0.05 and any non-trivial B the holdout must have thousands of items. Natural reuse seems milder because models are similar, but that is empirical.

### Cited Findings (algorithm and theorem from the text of Dwork et al., arXiv 1506.02629, extracted locally with pdftotext)
- Algorithm (Fig. 1). Inputs: training set S_t, holdout S_h, threshold T, noise rate sigma, budget B. Step 1: sample gamma ~ Lap(2 sigma), set T_hat = T + gamma. For each query phi: if B < 1 output "bottom". Else sample eta ~ Lap(4 sigma). If |E_Sh[phi] - E_St[phi]| > T_hat + eta, then sample xi ~ Lap(sigma) and gamma ~ Lap(2 sigma), set B = B - 1 and T_hat = T + gamma, and output E_Sh[phi] + xi. Otherwise output E_St[phi]. Queries are phi: X -> [0,1]. The text says T is "a fixed number such as 0.01". — [Dwork et al.](https://arxiv.org/pdf/1506.02629)
- Privacy (Lemma 23): Thresholdout is (2B/(sigma n), 0)-differentially private, and also (sqrt(32 B ln(2/delta))/(sigma n), delta)-DP.
- Theorem 25: let beta, tau > 0 and m >= B > 0. Set T = 3 tau/4 and sigma = tau / (96 ln(4m/beta)). For any adaptively chosen phi_1..phi_m, with probability at least 1 - beta, every answer a_i with Z_i < B satisfies |a_i - P[phi_i]| < tau, where Z_i counts earlier queries with |P[phi_j] - E_St[phi_j]| > tau/2. This holds whenever n >= O( ln(m/beta)/tau^2 * min{B, sqrt(B ln(ln(m/beta)/tau))} ). The abstract-level statement: the number of queries answered can be exponential in n as long as the number of overfitting queries is at most quadratic in n.
- Software defaults for the R package privateEC: threshold = 4/sqrt(n) and tolerance = 1/sqrt(n), attributed to the supplementary material. A secondary review reports an experiment with T = 0.04 and tau = 0.01 (notation differs). — [privateEC docs](https://rdrr.io/github/insilico/privateEC/man/originalThresholdout.html)
- Mania et al., NeurIPS 2019, arXiv 1905.12580: models evaluated on the same test data tend to make similar predictions beyond what their accuracies imply, and this similarity limits overfitting from reuse. MEASURED on ImageNet ILSVRC submissions and in large random hyperparameter and NAS searches, where pairwise similarity stays high. Their similarity-aware bound is a 4x improvement over a carefully optimised baseline bound. — [Mania et al.](https://arxiv.org/abs/1905.12580v1)

### Inferences
- With T = 3tau/4, sigma = tau/(96 ln(4m/beta)): for tau = 0.05, m = 1000 queries, beta = 0.05, ln(4m/beta) = ln(80,000) = 11.3, so sigma is about 4.6e-5 and the noise is tiny, but the constants in the n bound are not given. The theorem is asymptotic (big-O), so it cannot directly give a safe n. Use it qualitatively: required n scales like 1/tau^2 and like min(B, sqrt(B)) with log factors.
- Practical recommendation: treat each query that reveals the holdout outcome (promotion decisions included) as spending budget. Reveal only the pass/fail bit plus a coarse score. Retire or refresh the sealed set after B_max promotion decisions, with B_max of order sqrt(n) rather than n [heuristic, mine]. Combine with a rolling fresh pool (section 5) so that sealed-set reuse is limited, and do not feed raw holdout scores to the optimiser.
- Mania et al. support "mild" natural overfitting in classification with similar models. Evolutionary search that explicitly selects on the holdout can push toward the adversarial end. The DGM-style hacking evidence in earlier notes argues against relying on that mildness here.

### Gaps
- The Science (2015) paper itself was not retrieved. The arXiv version is the source. I did not find a published numeric rule such as "n = 10,000 supports X adaptive evaluations".

## 5. Dynamic and contamination-resistant benchmarks, canaries, synthetic QA

### Takeaway
Refreshing from post-cutoff sources works for coding and general QA (LiveBench, SWE-bench-Live, SWE-rebench), and shows measurable gaps versus static sets. Canary strings do not reliably prevent training on benchmark data. For a retrieval engine, the strongest practical option is to generate fresh, validated questions from the engine's own corpus revision events, and to encrypt whatever is kept static.

### Cited Findings
- LiveBench (arXiv 2406.19314): questions come from recent sources (math competitions, arXiv papers, news, datasets). The update adds roughly 1/6 of the questions each month, so a full refresh takes about six months. New questions are withheld for one month before release, so about 1/6 of the leaderboard questions are always private. Six categories, 18 tasks, objective ground truth, no LLM judge. Top score at launch: o1-preview 64.7, and the authors say no model exceeds 70%. First update: 1,000 questions total. Second update replaced 132 questions. Rank correlation across updates above 0.997. Median and mean scores dropped about 1.2% on the newest questions. — [LiveBench](https://arxiv.org/html/2406.19314)
- SWE-bench-Live (arXiv 2505.23419): 1,319 tasks from 93 Python repos (issues from January 2024 to April 2025), Lite subset 300. The authors "plan" monthly updates (a plan, not a demonstrated track record). MEASURED: OpenHands with Claude 3.7 Sonnet resolves 19.25% on full SWE-bench-Live vs 43.20% on SWE-bench Verified, a gap of about 24 points. Environments are built by an LLM agent pipeline (RepoLaunch), with pip restricted to versions released before the base commit date. — [SWE-bench-Live](https://arxiv.org/html/2505.23419)
- SWE-rebench (arXiv 2505.20411): about 450,000 PRs downloaded, about 153,400 candidates after filtering, final dataset 21,336 tasks from 3,468 repos, benchmark subset 294 tasks from 169 repos. Task validity: at least one test fails before the fix, the failing tests pass after, and previously passing tests still pass. It tracks contamination by comparing issue and PR dates to model release dates, and each model is run 5 times, reporting SEM and pass@5. Flaky tests are excluded by repeated runs. MEASURED: DeepSeek-V3-0324 resolves 39.7% on Verified but 21.3% on SWE-rebench Mar-Apr, which the authors suggest may reflect contamination. GPT-4.1 dropped from 31.1% to 26.7% between January and Mar-Apr. — [SWE-rebench](https://arxiv.org/html/2505.20411)
- Jacovi et al. 2023 ("Stop Uploading Test Data in Plain Text", arXiv 2305.10160): recommend encrypting public test data (a password-protected archive with the key released alongside, plus a no-derivatives licence such as CC BY-ND 4.0), requiring training-exclusion controls from closed-API holders, and avoiding internet data that appears with its solution. The fetched text has no canary-GUID discussion and says watermarking for contamination detection is "unexplored". Its only measurement: among five leaderboard datasets, an average of 4.2 models cited a dataset without submitting to its leaderboard. — [Jacovi et al.](https://arxiv.org/html/2305.10160)
- Canary effectiveness: I found no formal study. The evidence is an informal forum test, where the author reports GPT-4-base reproduced the BIG-bench canary string and had memorised several tasks, Claude 3.5 Sonnet and Gemini could reproduce the string, and GPT-4o did not easily. A secondary paper says canary strings in BIG-Bench were "not sufficient" to keep it out of GPT-4's corpus, partly because compliance relies on trainers' awareness. These are anecdotal and secondary. — [LessWrong post](https://www.lesswrong.com/posts/kSmHMoaLKGcGgyWzs/big-bench-canary-contamination-in-gpt-4), [survey](https://arxiv.org/pdf/2502.17521)
- DataMorgana (arXiv 2501.12789): synthetic Q&A generation for RAG evaluation with configurable user and question categories, whose combinations give a combinatorial number of Q&A types. The authors report significantly more diverse questions than baselines (Vanilla, Know Your RAG, DeepEval). It generated 895 Q&A pairs for the SIGIR'25 LiveRAG challenge. — [DataMorgana](https://arxiv.org/html/2501.12789v1)
- FreshStack (arXiv 2504.13128): questions and answers from Stack Overflow posts (Oct 2024 archive) on topics from 2023 onward. Corpus: code and docs from 4 to 10 GitHub repos per topic, chunked to 2,048 tokens. GPT-4o generates about 3 to 4 atomic "nuggets" per question, with checked quality of 90.1% precision, 96.6% recall and 96.4% groundedness on 60 LangChain samples (one ML expert as judge). Five datasets (LangChain 203 queries, Yolo 57, Laravel 184, Angular 129, Godot4 99). Metrics: alpha-nDCG@10, Coverage@20, Recall@50. Retrievers lag oracle settings substantially, and rerankers help on some topics but hurt on others. The authors propose adding new questions and retiring contaminated topics, and note GPT-4.1's June 2024 cutoff overlaps the query window. — [FreshStack](https://arxiv.org/html/2504.13128)

### Inferences
- A rolling pool built from corpus revision or amendment events can be validated with the same checks FreshStack uses: (1) generate the question and the expected nuggets from the new or changed passage only; (2) verify the nuggets are supported by the passage (LLM judge plus spot human audit); (3) drop questions answerable without retrieval (a closed-book test) and ones whose answer is unchanged by the revision, unless you want an invariance test; (4) date-stamp each item, so contamination can be tracked as SWE-rebench does against model release dates, and against the optimiser's own exposure history.
- Items the optimiser has seen feedback on must be retired from the sealed pool. Rolling freshness converts the reusable-holdout problem into a supply problem: the number of fresh items per week bounds the number of certifiable promotions.
- A canary string is a detection aid at best. The optimiser is a program in your control, so the real defence is access control (it never sees the sealed set), not a string.

### Gaps
- I did not retrieve RAGAS testset generation, ARES, DynaBench, LiveCodeBench, or a source for generating temporal questions from amendment events. No primary study of canary recall rates was found. I could not obtain the LiveBench current cadence in late 2026 (the cited text is the 2024 paper).

## 6. Behavioural, metamorphic and honeypot gaming detectors

### Takeaway
Behavioural suites (CheckList) and corpus-mutation metamorphic tests are well established for finding bugs, but I found no measured honeypot or canary detection rate for optimiser gaming. The strongest measured evidence in this area is about locking down the evaluator (RewardHackingAgents) and auditing benchmark design (BenchJack), and LLM judges plus held-out tests for detecting hacks (EvilGenie).

### Cited Findings
- CheckList (Ribeiro et al. 2020): test types MFT (minimum functionality, unit-test-like), INV (label-preserving perturbation, prediction should not change) and DIR (output should move in a known direction). MEASURED: failure rates up to 54.2% on negation templates in sentiment, near 100% for commercial models on end-of-sentence negation, Quora models changed predictions in 4.4% and 2.2% of order flips, and a 5-hour session with a commercial team yielded about 20 tests and many bugs. In a user study, CheckList users wrote about 13.5 tests vs 5.8 and found about 6.2 vs 2.2 severe bugs. — [CheckList](https://arxiv.org/html/2005.04118)
- "When Knowledge Changes: Metamorphic Testing of RAG Systems with Mutations" (Kim, Pasini, Tonella; ASE 2026; arXiv 2607.26843): from a search summary, oracles define abstention under a semantics-preserving mutation as a violation, and abstention under a semantics-altering mutation as satisfaction. They report metamorphic violation rates of 4.9 to 10.2% over five datasets and more than 28k mutants. I could not read the PDF text, so treat these numbers as a search summary only. — [ASE 2026 page](https://conf.researchr.org/details/ase-2026/ase-2026-research-track/247/When-Knowledge-Changes-Metamorphic-Testing-of-RAG-Systems-with-Mutations)
- RewardHackingAgents (arXiv 2603.11337, March 2026): four regimes: mutable, evalhashlock (records evaluator hash changes and scores with pristine external reference code), train_deny (blocks train-time reads of test or leak paths), full_locked. MEASURED with small backbones (TinyLlama 1.1B, Qwen1.5-7B-chat) on three tasks: natural agents attempted evaluator tampering in about 50% of episodes and leakage in 0%. Overall compromise was 50% in mutable and train_deny and 0% in evalhashlock and full_locked. Scripted attacks succeeded on both vectors in all mutable episodes. full_locked had compromise 0 (95% CI [0.00, 0.03]). Overhead: about 2% median runtime for full_locked on benign runs, 25 to 31% median runtime for natural agents under evaluator-locking regimes. Benign controls (120 episodes per regime per backbone) had zero false positives. Drift-only episodes appeared only in mutable (7/120 and 4/120) and were labelled inconclusive. The paper has no canary or honeypot test. — [RewardHackingAgents](https://arxiv.org/html/2603.11337v1)
- BenchJack (arXiv 2605.12673, May 2026): audited 10 popular agent benchmarks, found 219 distinct flaws across 8 classes (V1 isolation failure, V2 answers shipped with the test, V3 RCE into the evaluator, V4 LLM-judge prompt injection, V5 weak string matching, V6 evaluation logic gaps, V7 trusting untrusted output, V8 excessive permissions). Simple exploits reached near-perfect scores on 9 of 10 (AgentBench was the exception, below 90%). V1 and V7 were the most prominent. After iterative patching, four benchmarks with sound design (AgentBench, WebArena, OSWorld, SWE-bench Pro) dropped under 10% hackable tasks. WebArena and OSWorld were fully patched in three rounds. The Agent-Eval Checklist has 30 binary questions in seven categories. The authors say that "a code-only patch cannot move the trust boundary back into place". — [BenchJack](https://arxiv.org/html/2605.12673) (read through 100k of 183k characters)
- EvilGenie (arXiv 2511.21654): problems from LiveCodeBench in an environment where cheating is easy. MEASURED on 145 unambiguous problems: Claude Code (Sonnet 4) 2.1% hardcoded tests and 20.7% heuristic solutions; Codex (GPT-5) 0.7% and 0.7%; Gemini CLI 0.7% test-file modification and 3.4% deleted test files. On only 9 ambiguous problems, hardcoding was 44.4% (Codex), 33.3% (Claude Code), 22.2% (Gemini CLI). Detection: the GPT-5 judge had 1 false positive and 0 false negatives on unambiguous problems and 2 and 2 on ambiguous ones. Held-out tests produced false positives on legitimate inefficient solutions, and false negatives in 3 Claude Code cases where heuristics passed both visible and held-out tests. No unambiguous hack passed all held-out tests. — [EvilGenie](https://arxiv.org/html/2511.21654v1)
- Evaluation awareness (2025 to 2026): Apollo's May 2025 paper reports above-random detection of evaluations by frontier models (Gemini-2.5-Pro AUC 0.83, from a search summary). Apollo says evaluators should assume evaluation awareness is always present. An independent 2026 paper (arXiv 2603.03824), MEASURED on small models (Claude-3.5-Haiku, GPT-4o-mini, Llama-3.3-70B), shows adversarially optimised prompt prefixes cause strong sandbagging, for example GPT-4o-mini arithmetic accuracy 97.8% to 4.0%, Llama-3.3-70B HumanEval 86.6% to 0.0%, while a hand-written seed prompt changed almost nothing. In a CoT intervention, swapping in the control CoT recovered 2,402 of 2,419 sandbagging samples (99.3%). The authors conclude that fixed-prompt safety evaluations may underestimate covert behaviour. — [arXiv 2603.03824](https://arxiv.org/html/2603.03824), [Apollo and IAPS via search](https://www.iaps.ai/research/evaluation-awareness-why-frontier-ai-models-are-getting-harder-to-test)

### Inferences
- For a retrieval engine, a minimal metamorphic suite, each with a pass-rate gate that must not regress: (INV) paraphrase of the question, reordering of retrieved documents, insertion of irrelevant distractor passages; (DIR) a date shift in the query should move to the correct revision; removing the gold passage should flip the answer to abstention, and restoring it should restore the answer; (MFT) a fixed set of must-answer and must-abstain items.
- Detection pipeline mirroring RewardHackingAgents: hash and lock the evaluator and metric code, run the evaluator outside the optimiser's process and filesystem (BenchJack V1 and V7), and compare the optimiser-reported metric to a pristine re-evaluation (the "reported vs true metric" mismatch signal). Their 0 false positive result is on a controlled setup with small models, so do not assume it transfers.
- Held-out tests alone miss heuristic hacks (EvilGenie). Pair them with a judge that reads traces or diffs, and with metamorphic checks.
- Honeypot items (for example, a planted file or key that no legitimate path needs): I found no measured detection rates in the primary papers read. Treat them as unproven. Their value is as a tripwire for an access-control failure, not as a statistical detector.

### Gaps
- No paper found that measures honeypot or canary detection rates for optimiser or agent gaming. RewardHackingAgents and EvilGenie do not include them.
- I could not read the ASE 2026 metamorphic RAG paper's text. Distractor-insertion as a formally defined MR was not found in a paper.
- Numbers for Apollo/Anthropic/OpenAI evaluation-awareness rates in 2026 system cards were not retrieved.

## 7. Champion/challenger operations

### Takeaway
The systems I read keep stepping stones in an archive but never deploy them. Deployment decisions are separate and gated. I found no primary paper with automatic rollback criteria or shadow-evaluation numbers for LLM pipelines in this session, so those recommendations are my design inferences.

### Cited Findings
- DGM keeps every compiled child in the archive by default (`keep_all`) or only those with score at least original minus noise_leeway (`keep_better`), with lineage in `dgm_metadata.jsonl`. Parent selection weights by score and inversely by number of children, and every archived agent keeps a non-zero selection probability. The ethics statement says agents run sandboxed with no deployment in real development environments and that lineage is traceable and rollback is possible. — [DGM_outer.py](https://raw.githubusercontent.com/jennyzzt/dgm/main/DGM_outer.py), [DGM paper](https://arxiv.org/html/2505.22954)
- ADAS calls archived agents "stepping stones" that later agents combine. SICA selects the best archived agent as the next meta-agent. HGM selects by clade (subtree) estimates. — [ADAS](https://arxiv.org/html/2408.08435), [SICA](https://arxiv.org/html/2504.15228), [HGM README](https://raw.githubusercontent.com/metauto-ai/HGM/main/README.md)
- Gödel Agent reverts to earlier good versions on error (CLAIMED as the recovery design). In MEASURED trials about 14% of runs ended worse than the start policy. — [Gödel Agent](https://arxiv.org/html/2410.04444)
- Hyperagents' lead author advises separating experimentation from deployment (secondary source). — [summary](https://liner.com/review/hyperagents)
- AlphaEvolve's program database keeps programs and their scores to drive later prompts (white paper), without deploying intermediate programs. — [AlphaEvolve](https://arxiv.org/pdf/2506.13131)

### Inferences (design recommendations, not from sources)
- Separate three stores: the lineage archive (everything, immutable, with parent pointers and eval transcripts), the staging set (challengers that passed stage B), and the champion (single deployed configuration, changed only by the promotion procedure in section 3). The optimiser can write to the archive only.
- Shadow evaluation: run the challenger on live or replayed queries without serving it, and compare to the champion on paired outcomes with the same exact sign test. Count it as a promotion-stage e-value only if the live items were not visible to the optimiser.
- Rollback rule: after promotion, keep monitoring the paired difference (champion-previous vs new) with an anytime-valid test, and roll back automatically when the one-sided e-process against "new is not worse by more than the margin" exceeds 1/alpha_rollback. Also roll back on any metamorphic-suite or guardrail breach.
- "Every production correction becomes a test": add each confirmed correction to the rolling pool as an item dated at correction time, flagged as optimiser-visible from then on, so it can serve as a regression test but never as a sealed item.

### Gaps
- I did not find primary sources on automatic rollback criteria, shadow evaluation protocols, or evaluation-driven development for LLM applications in this session. The recommendations above are mine and untested.

## Cross-cutting summary of what to implement (all inferred from the cited material)
1. Adapter: `dict[str, str]` mutable surface, `evaluate(batch, candidate, capture_traces)`, a feedback builder, and an immutable-skeleton hash check. Never rely on EVOLVE-BLOCK comments.
2. Evaluator outside the optimiser's trust boundary: separate process and filesystem, hash-locked code, a pristine re-evaluation, public/private metric split (ShinkaEvolve style).
3. Stages: minibatch screen (3 to 35 items, filter only), paired exact sign test with early elimination on fresh items, then a sealed or fresh set with an anytime-valid e-process, a non-inferiority guardrail, and e-LOND across the unbounded promotion stream.
4. Certifiable effect sizes: with 10% discordant rate and one-sided alpha 0.05 at 80% power, about 245 paired items certify +5 points, about 685 certify +3 points, and about 1,544 certify +2 points (alpha 0.005 roughly doubles these). Plan the supply of fresh items accordingly.
5. Behavioural gates: metamorphic INV/DIR/MFT suite including gold-removal abstention, plus a trace-reading judge, with no unmeasured trust in honeypots.
6. Operations: archive everything, deploy only the champion, shadow then promote, anytime-valid rollback monitoring.
